# Journal des changements affectant le benchmark

Une ligne par changement constaté ou apporté qui affecte la
comparabilité d'un trimestre à l'autre : évolution du prompt de prod,
changement de config par défaut (modèle, température, tokens), mise à
jour du protocole ou du jeu de données lui-même, changement d'appareil
de test pour Nano, etc.

| Date | Changement | Impact attendu sur la comparabilité |
|---|---|---|
| 2026-08-22 | Création initiale du protocole et du jeu de données | — (référence de départ) |
| 2026-08-22 | Run #1 (baseline) : échec sur les 2 cas — texte vide renvoyé par `gemini-3.5-flash`, cause probable : le budget de réflexion ("thinking") consomme tout `maxOutputTokens` (1024) avant que le JSON attendu ne soit généré. Bug de fiabilité applicatif réel identifié en parallèle : la boucle de repli entre modèles ne se déclenche pas sur ce cas (200 OK avec texte vide traité comme succès définitif) — voir issue #158. | Aucune évaluation de qualité possible sur ce run — à refaire une fois #158 corrigé, ou en attendant via un run `prompt_variant_id` distinct forçant `--model gemini-1.5-flash` (pas de réflexion, contourne le problème) pour au moins juger la qualité du texte généré. |
| 2026-08-23 | Confirmation empirique : `maxOutputTokens=4096` (au lieu de 1024, tout le reste inchangé) fait passer les 2 cas sur `gemini-3.5-flash` — cause racine confirmée. Voir issue #158. Au passage : `gemini-1.5-flash` et `gemini-2.5-flash-preview-05-20` (repli configurés en prod) sont tous les deux totalement retirés par Google ; toute la famille 2.5 (`gemini-2.5-flash`, `-lite`) s'est aussi révélée inaccessible à cette clé API ("no longer available to new users"), malgré une doc/recherche web qui laissait penser le contraire — se fier à `--list-models` plutôt qu'à des sources externes pour choisir un modèle de test. | Prochain run "officiel" trimestriel à faire avec un `maxOutputTokens` de prod corrigé (voir #158 pour la valeur retenue) plutôt que le défaut actuel de 1024, sans quoi le run échouera à nouveau. |
| 2026-08-23 | Premier run cloud complet obtenu (`gemini-3.5-flash`, `maxOutputTokens=4096`, style immersive) sur les 2 cas du jeu de données. Constat qualité : sur `notre_dame_paris` (sujet très documenté), le script ne contient que des faits réels et vérifiables. Sur `notre_dame_vincennes` (lieu local peu connu), le script invente un nom d'architecte et des détails de financement absents du `location_context` figé — hallucination plausible mais non vérifiée, à noter dans la grille de notation (exactitude factuelle) plutôt qu'à prendre pour argent comptant malgré un texte bien écrit. | — |
| 2026-08-23 | Volet Nano non réalisé pour ce trimestre : pas d'appareil physique compatible AICore disponible au moment du run. Confirmé que Gemini Nano/AICore ne fonctionne pas sur émulateur Android (limitation connue de la plateforme, pas propre à AudioLens) — impossible de contourner sans accès matériel réel. | À refaire dès qu'un appareil compatible (Pixel 8+, Galaxy S24+, ou autre modèle listé dans PROTOCOL.md) est disponible — pas de comparaison cloud/on-device possible pour ce trimestre en attendant. |
| 2026-08-25 | Issue #167 : `location_context` des deux cas existants remplacé par le vrai résultat du pipeline de production (`LocationContextResolver` — reverse geocoding Nominatim, recherche POI Overpass, extraits Wikipedia réels par géolocalisation et par nom), au lieu du paraphrase manuel de ~250 caractères créé avec le dataset. `notre_dame_paris` passe de ~280 à 3828 caractères (5 extraits Wikipedia fusionnés, POI trouvé : « Notre-Dame de Paris ») ; `notre_dame_vincennes` passe à 1022 caractères (3 extraits, aucun POI trouvé — la requête Overpass a expiré à plusieurs reprises, un résultat vide réaliste que `PoiService` produirait aussi en production dans ce cas). Résolu via un script Python ponctuel (non committé) répliquant exactement les endpoints/paramètres de `wikipedia_service.dart`/`poi_service.dart`/`location_service.dart`, pas via `flutter test` (les appels réseau du client HTTP Dart échouaient avec un 400 dans cet environnement sandboxé, cause non identifiée — `curl` vers les mêmes URLs fonctionnait normalement). | Les comparaisons avec le run trimestriel précédent (2026-08-23) ne sont plus strictement valables pour ces 2 cas, puisque le contexte d'entrée a changé — attendu et documenté, pas une régression. Reste ouvert : ajouter un cas sans aucun contenu Wikipedia disponible (suggéré par #167), pas fait ici faute d'une nouvelle photo/GPS à disposition. |
| 2026-08-27 | Ajout d'un 3e cas au jeu de données : `stolperstein_fontenay_sous_bois` (catégorie `sujet_ambigu`) — un pavé de mémoire (Stolperstein) au sol, photo fournie par l'utilisateur suite à un test manuel dans le Nano Prompt Lab (#272) révélant que le modèle décrit vaguement la plaque sans jamais identifier le type de mémorial, alors qu'il connaît le concept en pur texte (connaissance non connectée à l'image). `location_context` résolu via le même pipeline de production que le run du 2026-08-25 ci-dessus — Overpass a trouvé le Stolperstein lui-même comme POI OSM tagué, poiName exact ("Umberto Chignoli"), contrairement aux 2 autres cas. | Élargit la couverture du jeu de données à un cas où la reconnaissance nécessite de mobiliser une connaissance générale au-delà de la description visuelle de surface — jusqu'ici non couvert par les 2 cas existants (tous deux des monuments/églises directement descriptibles). Comparaisons trimestrielles antérieures inchangées (les 2 cas existants ne bougent pas), ce cas n'a simplement aucun historique avant cette date. |
